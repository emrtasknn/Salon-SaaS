# Task — Salon SaaS · WP-06 Customer status link + customer self-cancel (ADR-044 phase 2)

## Objective
After booking, a guest gets a tenant-scoped, unguessable status link. The page shows the appointment and lets the customer cancel a PENDING or CONFIRMED appointment.

## Risk class
C3 — migration (new table + RLS), booking write path, new public unauthenticated surface, new actor triggering a lifecycle transition.

## Context
- `docs/ADR-044-NOTIFICATION-CHANNELS.md` §5, §7, §8, §9 phase 2, §10.4 (expiry `endAt + 7 days`), §10.5 (self-cancel amendment 2026-11-04).
- `docs/PROJECT_GOVERNANCE.md` §4, §7 (`PENDING/CONFIRMED → CANCELLED` already valid; transactional rules).
- `docs/RLS_TENANT_ISOLATION.md`, `docs/AUTHORIZATION_COMPOSITION.md`. WP-05 limiter applies to reads and cancel.

## Scope
In: new `AppointmentAccessToken` (hash only, tenant, appointment, expiry, revoked; RLS); token created inside the booking transaction; link on booking success; new `src/app/[slug]/randevu/[token]/page.tsx`; cancel action re-checking token, tenant slug, expiry and status server-side.
Out: reschedule; customer accounts; customer Web Push.

## Acceptance criteria
- [ ] Only the token hash is stored; raw token never logged.
- [ ] Tenant A's token is unusable under tenant B's slug; expired/revoked tokens get a generic not-found.
- [ ] Cancel only from PENDING/CONFIRMED via the existing transition logic, idempotent, rate-limited.
- [ ] Two-tenant RLS integration test for the new table (CI); existing public-booking and notification suites green.
- [ ] **Owner decisions (stop):** (a) cancel cutoff before `startAt`; (b) notify staff/admin on customer cancel (new `NotificationEventType` = migration, or in-app only via WP-04); (c) Turkish route name `randevu`.
- [ ] Workflow: salon-saas-database → ⛔ owner (migration + booking rule) → salon-saas-backend ∥ salon-saas-uiux → salon-saas-qa (unit + two-tenant) → lint/typecheck → salon-saas-reviewer → ⛔ merge → ⛔ apply approval.

**Design**
- Token: generated in application, only `tokenHash` reaches persistence; insert inside booking tx (failure rolls booking back). Raw token never passed to `publishAppointmentNotification`, never logged.
- View: limiter `status.view` → slug→tenant server-side → `withPrismaTenantContext` lookup by `(tenantId, sha256(token))`, `revokedAt null`, `expiresAt > now` → minimal fields (salon, service, staff display name, start/end, status; no phone/email/notes). All failures = one generic `NOT_FOUND`; misses also hit `status.miss`.
- Cancel: action takes `(slug, token)` only. One tx: re-check token → cutoff → `transitionAppointmentStatus` → `updateMany {tenantId,id,status:from}`. Already CANCELLED → idempotent success. New actor "token holder" (does not reuse `booking-engine.transition`, which is admin-only) → **owner approval**.

**Gaps:** ADR-044 §7 assumes one combined migration (§9 allows split; annotate). WP-05 doc surfaces table still lists removed `submitPublicBooking`. Limits inactive until `TRUSTED_IP_HEADER` exists (token entropy is the only guard until then). No cancel actor/audit trail (known limitation). Inactive tenant handling undefined (recommend: page stays readable).

### 2026-11-04 — salon-saas-database (proposal, not applied)

**Migration:** `prisma/migrations/20261104110000_appointment_access_token/migration.sql` (after WP-05 `20261104100000_rate_limit`). Additive only, no enum/column/data changes, no backfill. Not run anywhere; CI (isolated PG 17) validates, apply needs owner approval.

**Policies** (ENABLE + FORCE RLS, `"tenantId" = current_setting('app.tenant_id', true)`): `appointment_access_token_tenant_isolation_select` / `_insert` / `_update` (USING + WITH CHECK) / `_delete`.

**Design notes**
- Model matches ADR-044 §5.1. Composite FK `(tenantId, appointmentId) → Appointment(tenantId, id)` + `tenantId → Tenant`, both `ON DELETE RESTRICT ON UPDATE CASCADE` (same as `NotificationDelivery`). Appointments are never hard-deleted by the app; RESTRICT means test cleanup must delete tokens before appointments.
- Uniques: `(tenantId, id)`, `(tenantId, tokenHash)` (lookup path), `(tenantId, appointmentId)`.
- **One token per appointment (recommended):** reissue = `UPDATE` the row (new `tokenHash`, new `expiresAt`, `revokedAt = null`), which kills the old link atomically; revoke = set `revokedAt`. Keeps lookup and cleanup simple and bounds rows per booking. Trade-off: no history of earlier tokens (not needed in MVP; no reissue flow in scope). If multi-link/history is ever needed, drop this unique in a later migration and add `@@index([tenantId, appointmentId])`.
- `tokenHash` is `TEXT` (Prisma default) with a manual CHECK `"AppointmentAccessToken_tokenHash_sha256_hex_check"` = `^[0-9a-f]{64}$` → raw base64url tokens cannot be stored by mistake. Prisma-invisible (like RLS); `migrate diff` ignores it, so no drift.
- No `updatedAt` (per ADR model). `expiresAt = endAt + 7d` is set by the application (ADR-044 §10-4), not by DB default.
- No GRANTs (existing tenant tables have none). No index on `expiresAt` (no cleanup job in scope).
- Rollback: `DROP TABLE "AppointmentAccessToken";` + revert schema/app code. Data impact: all status links become "invalid or expired"; appointments untouched.

**Integration-test outline** — `src/persistence/prisma-appointment-access-token.integration.test.ts` (CI only; seed tenants A and B each with staff/service/profile/appointment via existing fixtures; tokens created inside `withPrismaTenantContext`):
1. Same-tenant: A inserts token for A's appointment and reads it back by `(tenantId, tokenHash)`.
2. Cross-tenant SELECT: under B's GUC, `findMany`/lookup by A's `tokenHash` (with and without `tenantId` filter) returns nothing.
3. Cross-tenant INSERT: under B's GUC, inserting a row with `tenantId = A` fails (RLS WITH CHECK).
4. Cross-tenant UPDATE: under B's GUC, `updateMany` setting `revokedAt` on A's row affects 0 rows; A's row unchanged (verified under A). Under A's GUC, updating `tenantId` to B fails.
5. Cross-tenant DELETE: under B's GUC, `deleteMany` on A's row affects 0 rows.
6. No GUC: query outside tenant context returns 0 rows; insert fails.
7. Cross-tenant FK: under A's GUC, inserting `tenantId = A, appointmentId = <B's appointment>` fails (composite FK).
8. `tokenHash` format: 63/65 chars, uppercase hex, base64url raw token all rejected by CHECK; valid 64 lowercase hex accepted. Duplicate `(tenantId, tokenHash)` and second token for same appointment rejected (unique).
9. Booking rollback: force failure after token insert in the public-booking tx (or token insert failure, e.g. invalid hash) → neither appointment nor token persists (update `prisma-public-booking.integration.test.ts` too).
10. Appointment delete: deleting an appointment with a token fails (RESTRICT); succeeds after deleting the token.
11. Catalog check (optional): `pg_class.relrowsecurity` and `relforcerowsecurity` both true for `AppointmentAccessToken`; 4 policies present.

### 2026-11-04 — salon-saas-reviewer (proposal review)

Verdict: **no BLOCKING findings** in the DB change (schema + `20261104110000_appointment_access_token`). CI must still confirm `prisma migrate diff --from-migrations --to-schema-datamodel` is empty.

OK: 256-bit token; unsalted SHA-256 adequate (no pepper); hex CHECK; lookup-by-hash needs no constant-time compare; `endAt + 7d`; one-token-per-appointment rotation; RLS identical to NotificationDelivery; composite FK; token insert inside booking tx; Prisma-conventional names; no GRANTs = same posture as existing tables.

Implementation checklist (NON-BLOCKING, must be done):
1. Do not revoke the token on cancel (customer must still see CANCELLED).
2. One query `(tenantId, tokenHash, revokedAt IS NULL, expiresAt > now())` → one generic NOT_FOUND copy + status code for unknown/cross-tenant/expired/revoked, in view **and** cancel.
3. Raw token never reaches `publishAppointmentNotification` or a logger — unit-test it.
4. `next.config.ts` `headers()` for `/:slug/randevu/:path*` (no-referrer, noindex, no-store) + `export const dynamic = "force-dynamic"`; verify header in build/e2e.
5. Cancel: token by `(tenantId, tokenHash)`, appointment by `(tenantId, token.appointmentId)`; on 0-row `updateMany` re-read in same tx and retry once (PENDING→CONFIRMED race); REJECTED/COMPLETED → generic "cannot cancel"; CANCELLED → idempotent success.
6. Cancel counts against `status.view` (or new `status.cancel`), misses against `status.miss`.
7. Structured log on customer cancel (tenant, appointment, actorKind), never the token.
8. Annotate ADR-044 §7 (split migration; grants consistent with existing tables). P8 checklist: token in URL path appears in hosting logs (retention); limiter inactive until `TRUSTED_IP_HEADER`.
