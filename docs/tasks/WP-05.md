## Design

### Store (draft migration on this branch)
- `prisma/migrations/20261104100000_rate_limit/migration.sql` — table `private."RateLimitBucket"` + function `private.rate_limit_hit(key, bucket, window_seconds)`. See the "Database proposal" section below.
- One row per key, fixed window. Atomic single `INSERT … ON CONFLICT (key) DO UPDATE` that resets `count` to 1 when the window changed and returns `(hit_count, window_start)`.
- Fixed window over sliding: cheaper, tiny table; up to 2× burst at a window edge is acceptable for these limits.
- Called with `$queryRaw` as its own statement **before and outside** the booking tenant transaction; needs no `app.tenant_id`.

### Keys and PII rules
- `key = hex(HMAC-SHA256(RATE_LIMIT_HMAC_SECRET, "v1|" + bucket + "|" + (tenantId ?? "-") + "|" + subject))`.
- Subject = client IP; IPv4 full address, **IPv6 normalised to its /64 prefix**. Missing/untrusted IP → IP buckets are **skipped** (see Client IP), never pooled into one shared key.
- HMAC with a server secret (not plain SHA-256): the IPv4 space is small enough to brute-force plain hashes.
- Only `bucket` (e.g. `booking.submit`) is stored in plain text. Raw IP, phone or email are never stored or logged.
- Phone bucket uses the normalised E.164 phone inside the HMAC input, scoped per tenant. Email is not used.
- New env var `RATE_LIMIT_HMAC_SECRET` (≥ 32 random bytes), server-only; added to the env example, never to client bundles.

### Client IP
- `getClientIp()` in `src/infrastructure/client-ip.ts` reads `await headers()` (Next 15+ async API; `request.ip` was removed in Next 15).
- Header trust is a deploy setting `TRUSTED_IP_HEADER`:
  - `x-vercel-forwarded-for` / `x-forwarded-for` (left-most value) only on Vercel, where the platform overwrites it.
  - `cf-connecting-ip` only behind Cloudflare.
  - unset, or header missing → no IP. Never trust a header the platform doesn't control.
- **No IP → skip the IP-keyed buckets** (`booking.submit`, `booking.submit.global`, `booking.availability`, `status.*`), keep the phone bucket, and log a warning (bucket only). A shared `"unknown"` key would act as a per-tenant global ceiling and block real customers — exactly what the design avoids.
- Hosting is not chosen yet (`docs/PROJECT_CONTEXT.md:40` — TBD P8), so IP limiting is inactive until it is (recommended: Vercel, see decisions).
- Limit inside each server action, not in `src/proxy.ts`: server actions are directly reachable POSTs and Next's docs say to check inside each function. Proxy-level limiting can be a later coarse layer.

### Limits (starting values, constants in code)
| Bucket | Key scope | Limit |
|---|---|---|
| `booking.submit` | tenant + IP | 5 / 10 min |
| `booking.submit.global` | IP (all tenants) | 20 / 1 h |
| `booking.submit.phone` | tenant + HMAC(phone) | 3 / 1 h |
| `booking.availability` | IP | 60 / 1 min |
| `status.view` (WP-6) | IP | 30 / 10 min |
| `status.miss` (WP-6) | IP, counts only invalid/expired tokens | 10 / 10 min |

No per-tenant global ceiling: an attacker could use it to lock a salon out of bookings.

### Behaviour when limited
- Server actions return a new result variant `{ status: "RATE_LIMITED", retryAfterSeconds }`, checked **before** any slot/booking logic. Booking semantics are unchanged; no appointment, slot hold or notification is created.
- Booking form copy (neutral, Turkish): "Çok fazla deneme yapıldı. Lütfen birkaç dakika sonra tekrar deneyin."
- WP-6 status page shows the same generic page as an invalid/expired link (no token oracle).
- Any future public route handler: HTTP 429 + `Retry-After`.
- If login is ever proxied server-side: same generic message as a wrong password (no account enumeration).

### Store errors
- Proposed **fail-open** with a structured log (bucket + error code only, no IP/key): a limiter fault never blocks real bookings. Status tokens are high-entropy, so fail-open is safe there too.
- Missing or short (< 32 bytes) `RATE_LIMIT_HMAC_SECRET` in production: **fail loudly at startup** via env validation, not silently at request time. A misconfiguration must not go unnoticed. Outside production (dev/CI) a missing secret disables the limiter with a warning.

### Cleanup / TTL
- No cron/worker infra exists. Opportunistic cleanup inside `rate_limit_hit`: with probability 1 %, delete up to 500 rows whose `window_start < now() - 1 day`. Longest window is 1 h, so 1 day is a safe margin.
- pg_cron or a platform cron can replace it later (separate approval).

## Database proposal
Draft: `prisma/migrations/20261104100000_rate_limit/migration.sql` (not applied anywhere; CI-only validation once approved).

- **No Prisma model.** `prisma/schema.prisma` has no `schemas`/multiSchema setting, and the precedent (`private.resolve_whatsapp_tenant_id`) keeps `private` objects out of Prisma. Access is a raw `$queryRaw` call to the function. `schema.prisma` is unchanged.
- **Table** `private."RateLimitBucket"(key PK, bucket, window_start, count, updated_at)`. CHECKs: key `^[0-9a-f]{64}$`, bucket `^[a-z][a-z0-9_.]{0,63}$`, `count >= 1`. Index on `window_start`. No tenant column (tenant is inside the HMAC).
- **RLS:** ENABLE + FORCE, like tenant tables. One policy `TO postgres` that admits rows only while the transaction-local flag `app.rate_limit_access = 'on'` is set (same idea as `app.tenant_id`). Only the function sets the flag and clears it before returning. Without this policy, FORCE RLS would deny the function itself on Supabase, where `postgres` is expected not to bypass RLS (tenant isolation depends on that).
- **Grants:** REVOKE ALL from PUBLIC, and from `anon` / `authenticated` when they exist (guarded `DO` blocks; CI's plain Postgres 17 has no such roles). `USAGE` on `private` + `EXECUTE` on the function to `postgres` only — the runtime role per the WhatsApp precedent and CI (`.github/workflows/ci.yml:28`).
- **Function** `private.rate_limit_hit(p_key, p_bucket, p_window_seconds) RETURNS TABLE(hit_count, window_start)`: SECURITY DEFINER, `SET search_path = ''`, input validation raising SQLSTATE `22023` (NULLs rejected; window 1..86400 s). Fixed window via `date_bin`. Single atomic upsert; `GREATEST(window_start)` so a transaction with an older `now()` never moves a row back and resets it. Cleanup at 1 % of calls: up to 500 rows older than 1 day, `FOR UPDATE SKIP LOCKED`.
- **Rollback:** drop function + table (header comment). Counters only; no business data lost.
- **Migration ordering:** timestamp `20261104100000` sits after `20261024120100_notification_delivery_unknown_legacy`. WP-6…WP-9 must use later timestamps.

### Caveats to confirm before any deploy
1. Read-only check on the target project (owner runs it, not an agent): `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = 'postgres';`. If `postgres` bypasses RLS, tenant isolation on existing tables is weaker than documented — a separate, bigger finding.
2. The runtime role also owns the table, so "function-only" is enforced by the flag policy, not by grants. Server code could still set the flag itself; a dedicated runtime role would be a separate decision.
3. Supabase pooler user (`postgres.<ref>`) is assumed to map to `postgres`; confirm against the real deploy.
4. CI connects as a superuser, so CI cannot prove the policy path the way Supabase will run it (see the test outline).

### Integration-test outline (`src/persistence/prisma-rate-limit.integration.test.ts`, CI only)
- First hit on a fresh random 64-hex key → `hit_count = 1`, `window_start = date_bin(now())`.
- N sequential hits in a 60 s window → 1..N.
- Rollover: seed a row with an old `window_start` (as owner) → next hit returns 1 with a newer window.
- Seeded row with a future `window_start` is not reset.
- 20 parallel hits on separate pool clients → returned counts are exactly {1..20}; stored count 20.
- Invalid input → `22023`: key uppercase / 63 chars / NULL; bucket `1abc` / `A` / 65 chars / NULL; window 0 / 86401 / NULL.
- `has_function_privilege('postgres', 'private.rate_limit_hit(text,text,integer)', 'EXECUTE')` is true.
- Non-owner role (pattern from `src/persistence/rls-tenant-isolation.integration.test.ts`: `CREATE ROLE … NOLOGIN`, `SET ROLE` inside a rolled-back transaction): no SELECT/INSERT/EXECUTE without grants (`42501`); with test-only table grants, rows stay hidden under FORCE RLS.
- Policy path: a non-superuser, non-BYPASSRLS test role that owns a copy of the setup (or is granted the policy) sees no rows without the flag and can hit through the function — so CI covers the Supabase-like path despite the superuser connection.
- Flag is cleared after the call: in one transaction, call the function, then `current_setting('app.rate_limit_access', true)` is empty.
- Cleanup: seed an expired row (> 1 day) and assert the DELETE removes it (bounded repeat, or test the statement directly); current-window rows are never deleted.
- `afterAll`: remove test keys and roles.
