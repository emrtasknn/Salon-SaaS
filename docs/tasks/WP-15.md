# Task — WP-15: Bind the WhatsApp sender to the pilot tenant (Faz 0)

Status: **Approved by owner 2026-11-16 (C3) and implemented, pending CI and review.** No schema change, no migration. Nothing was applied to any database.

## Objective
The configured WhatsApp sender (`WHATSAPP_*` server secrets) belongs to one real pilot business. Appointment WhatsApp messages are sent from it only for the tenant that owns it. Every other tenant gets no WhatsApp channel; in-app notifications and Web Push are unchanged.

## Risk class
**C3.** Changes notification sender routing and supersedes the shared-sender addendum in ADR-042 for the pilot phase.

## Context
- Owner decisions 2026-11-16:
  - Randevu'N has no tax certificate yet, so it cannot pass Meta business verification. It cannot own a platform sender or become a Tech Provider (no Embedded Signup) for now.
  - The project continues with one real pilot business and that business's own WhatsApp Business account.
  - No in-app messaging.
- Before this change `src/app/notification-runtime.ts` built one provider from env and used it for **every** tenant. With the pilot's token in env, another tenant's appointment would have been announced from the pilot salon's number.
- The self-service connection (Embedded Signup, encrypted per-tenant tokens, platform fallback sender) is Faz 1 and stays unapproved. Plan report: owner's "İşletmeye Özel WhatsApp Business Bağlantısı — Plan Raporu".

## Change
- `src/persistence/prisma-whatsapp-integration.ts` — `isWhatsAppSenderBoundToTenant(prisma, tenantContext, phoneNumberId)`: true only for an `ACTIVE` `META_WHATSAPP` `WhatsAppIntegration` row of that tenant with that phone-number id. Runs in `withPrismaTenantContext` (RLS) and filters by `tenantId`.
- `src/app/notification-runtime.ts` — the WhatsApp provider is created only when the configured `WHATSAPP_PHONE_NUMBER_ID` is bound to the server-side tenant context. Not bound → `provider: null` (no WhatsApp delivery rows). Check throws → logged (`whatsapp_sender_binding_check_failed`), `provider: null`, Web Push still publishes.
- Webhook routing is unchanged. Statuses on the configured number are still resolved by `providerMessageId`; delivery rows now exist only for the bound tenant.

## Rules kept
- Tenant comes from the server-side `TenantContext`, never from client input.
- Fail closed: missing, inactive or other-tenant integration → no WhatsApp send. No fallback to any other sender.
- RLS, booking semantics and the appointment state machine are untouched.

## Tests
- Unit: `src/persistence/prisma-whatsapp-integration.test.ts`, `src/app/notification-runtime.test.ts` (WP-15 block).
- Integration (CI only, isolated PostgreSQL 17): case (9) in `src/persistence/prisma-whatsapp-webhook.integration.test.ts` — under a non-bypass RLS role, a sender matches only its own tenant, in both directions, and not when `INACTIVE`.

## Operational steps (owner, each needs explicit approval; not done by this WP)
1. Pilot business: Meta business portfolio, app, WhatsApp account, number, approved appointment templates, payment method. Owner is added as admin.
2. Put the pilot's system-user token, phone-number id, app secret, verify token and template map into the server secrets. Never in source, chat or logs.
3. Ensure the pilot tenant has exactly one `ACTIVE` `WhatsAppIntegration` row with `provider = 'META_WHATSAPP'` and that phone-number id. Check the existing row first; this is a production data change.
4. Real-device test: created / confirmed / rejected and delivery status for the pilot tenant; a second test tenant must produce no WhatsApp delivery row.

## Open

- Unverified-business sending limits and the business-token lifetime are not verified against Meta's documentation (not reachable from the planning session).

## Remaining risks
- After deploy, tenants without a matching integration row stop receiving WhatsApp. If the live pilot row is missing or has a different phone-number id, the pilot tenant also stops until step 3 is done.
- `docs/P8_PRODUCTION_READINESS_CHECKLIST.md` gates still apply; this WP does not approve production use.
