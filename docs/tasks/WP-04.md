# WP-04 — In-app notifications (ADR-044 phase 1, §3 Option A)

## Objective
Staff and tenant admins see a badge and list of in-app notifications derived from `Appointment`. The list holds pending requests (`status = PENDING`) and recent status changes (`updatedAt`). There is no new table, no read/unread state, and no booking-semantics change.

## Risk class
**C2**: a new authorized read path scoped by tenant and staff. ADR-044 §10-1 Option A was accepted by the owner on 2026-11-04 (per the orchestrator brief). The ADR file still shows "Proposed" (see E1). No schema or migration.

## Context
- `docs/ADR-044-NOTIFICATION-CHANNELS.md` §3, §9 phase 1, §10-1
- `docs/PROJECT_GOVERNANCE.md` §4, `docs/SERVER_AUTHORIZATION_ENFORCEMENT.md`, `docs/RLS_TENANT_ISOLATION.md`
- `prisma/schema.prisma` `model Appointment`: has `updatedAt @updatedAt`; no `(tenantId, updatedAt)` index.
- Today only status transitions update `Appointment` (`src/persistence/prisma-booking-engine.ts`), so `updatedAt` ≈ last status change.

## Requirements
- **WP4-R1** Staff see only their own appointments (`staffId` = the ACTIVE `Staff` row for their membership profile, resolved server-side).
- **WP4-R2** Tenant admins (TENANT_ADMIN via `enforceServerAuthorization`) see the whole tenant.
- **WP4-R3** Pending: all `status = PENDING` in scope, `startAt` asc, `take 20`. Badge shows true `pendingCount` (separate count, not capped).
- **WP4-R4** Recent: `status IN (CONFIRMED, REJECTED, CANCELLED, COMPLETED)` and `updatedAt >= now − 7 days`, `updatedAt` desc, `take 20`.
- **WP4-R5** Tenant and staff scope come only from trusted server context. Server actions take **no arguments**.
- **WP4-R6** Refresh on navigation (server render) and on window `focus` / `visibilitychange → visible`. No polling, no read/unread, no client persistence.
- **WP4-R7** Minimal payload: `appointmentId, kind, status, startAt, updatedAt, serviceName, staffDisplayName`, plus `customerDisplayName` **for admins only** (E2). Never email or phone.
- **WP4-R8** Failures degrade safely: UNAUTHORIZED / PERSISTENCE_FAILURE render an empty/hidden badge and never break the host page.

## Scope
In: application service, Prisma repository, two no-arg server actions, a badge/list client component on `/staff`, `/staff/appointments`, `/admin`, `/admin/calendar`, unit + integration tests.
Out: schema/migration/index, `InAppNotification` table (Option B), Web Push, status link, polling/realtime, customer notifications, any change to `booking-engine` or transitions, a new layout.tsx.

## Query design
`src/application/in-app-notifications.ts`
- `RECENT_WINDOW_DAYS = 7; PENDING_LIMIT = 20; RECENT_LIMIT = 20`
- `InAppNotificationScope = { kind: "tenant" } | { kind: "staff"; staffId }`
- `InAppNotificationItem = { appointmentId; kind: "PENDING_REQUEST" | "STATUS_CHANGED"; status; startAt; updatedAt; serviceName; staffDisplayName; customerDisplayName? }`
- `InAppNotificationRepository.read(tenantContext, scope, { since, pendingLimit, recentLimit }) → { pendingCount, pending, recent }`
- `InAppNotificationAuthorizer = { authorizeAdmin(identity, tenantContext); authorizeStaffScope(identity, tenantContext, staffId) }`
- `createInAppNotifications({ repository, authorizer, now })` → `forAdmin(identity, tenantContext)`, `forStaff(identity, tenantContext, staffId)`; results `ok | UNAUTHORIZED | INVALID_INPUT | PERSISTENCE_FAILURE` (pattern of `calendar-crm.ts`). Staff results drop `customerDisplayName`.

`src/persistence/prisma-in-app-notifications.ts`: `createPrismaInAppNotificationRepository(prisma)`
- One `withPrismaTenantContext` transaction, three queries, each `where` with explicit `tenantId` (+ `staffId` for staff scope): count PENDING; findMany PENDING; findMany recent.
- Select only `staff.profile.displayName`, `customerProfile.displayName`, `service.name`.

Server actions (no args):
- `listStaffNotifications()` in `src/app/staff/actions.ts` via `getStaffContext()`.
- `listAdminNotifications()` in `src/app/admin/calendar-actions.ts` via `getAdminContext()` + `enforceServerAuthorization(..., "TENANT_ADMIN")`.

## Tests
- Application unit: UNAUTHORIZED → repo not called; staff scope uses given `staffId`; `since = now − 7d`; limits passed; repo throw → PERSISTENCE_FAILURE; staff items lack `customerDisplayName`.
- Persistence unit (mock tx): `set_config` first; every `where` has `tenantId`; staff scope adds `staffId`; status sets, `updatedAt.gte`, `orderBy`, `take` correct; no email/phone selected.
- Integration (CI): tenant A never sees tenant B; staff scope excludes other staff; old rows excluded.

## Acceptance criteria
- [ ] Staff badge = own PENDING count; admin badge = tenant-wide PENDING count.
- [ ] Recent list: non-PENDING updated in last 7 days, newest first, ≤ 20.
- [ ] Focus/navigation refreshes. No mutation, no booking change.
- [ ] Server actions take no client input.
- [ ] Lint, typecheck, unit tests, build pass; integration test passes in CI. No new dependency, no schema change.

## Escalation
- **E1** ADR-044 file still says "Proposed"; owner acceptance (2026-11-04) is recorded only via the orchestrator. Record it in the ADR (WP-0 docs session).
- **E2** `customerDisplayName` is not shown to STAFF (current staff UI shows none). Changing that needs owner approval.
- **E3** Any `(tenantId, updatedAt)` / `(tenantId, status)` index is a migration, out of WP-4. Acceptable at pilot volume.
- **E4** If `Appointment` is later updated for non-status reasons, `updatedAt` stops meaning "status change"; revisit or move to Option B.
