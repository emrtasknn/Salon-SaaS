# W11.5 — WhatsApp Acceptance Runbook (Test Ortamı)

## 1. Amaç ve Kapsam

Bu runbook, tek bir pilot tenant üzerinde gerçek WhatsApp akışının manuel doğrulaması için adım adım, güvenli bir kılavuktur. Yalnızca **test/pilot ortamı** içindir. Üretim ortamında çalıştırılmaz. Gerçek WhatsApp mesajı gönderilmeden önce `npm run whatsapp:preflight` ile yapılandırma doğrulanır.

Runbook mevcut kod (`src/app/notification-runtime.ts`, `src/infrastructure/notifications.ts`, `src/application/notification-service.ts`, `src/persistence/prisma-notification.ts`, `src/persistence/prisma-whatsapp-webhook.ts`) ve mevcut belgeler (`W11.5_META_WHATSAPP_PILOT_PLAN.md`, `W11.6_WHATSAPP_TENANT_ROUTING_C3.md`, `ROADMAP.md`) ile tutarlı olmalıdır.

## 2. Test Ortamı Önkoşulları ve Üretim/Test Ayrımı

| Önkoşul | Açıklama |
|---|---|
| Ortam | Yalnızca test/pilot/Supabase pilot projesi. Üretim veritabanı veya üretim Meta WABA kullanılmaz. |
| Sunucu tarafı | WhatsApp runtime tamamen sunucu tarafında çalışır (`server-only`). İstemci tarafına hiçbir secret sızdırılmaz. |
| Meta | Test WABA (WhatsApp Business Account), test phone number ID, onaylı test şablonları ve izinli alıcı numaraları gerekir. |
| Veritabanı | Test tenant’ı ve test kullanıcıları (owner, staff, customer) mevcut olmalıdır. |
| Seed | Pilot tenant için `WhatsAppIntegration` kaydı için mevcut seed/SQL yöntemi yoktur (blokaj #7). |

**Üretim ile ayrım:** Bu runbook üretim deployment’ı, üretim secret’lerini veya üretim Meta yapılandırmasını kapsamaz. Üretim onayı W11.9別도의 onay noktasıdır.

## 3. `npm run whatsapp:preflight` Çalıştırma ve Sonuç Yorumu

### Komut

```bash
npm run whatsapp:preflight
```

### Yorumlama

| Çıktı | Anlamı | Aksiyon |
|---|---|---|
| Tüm env var `SET` | Altı gerekli ortam değişkeni var | Şablon kontrolüne geç |
| Herhangi bir env var `MISSING` | Gerekli değişken eksik | Ortam değişkenini ekle, tekrar çalıştır |
| `parse: OK` | `WHATSAPP_TEMPLATES_JSON` geçerli JSON | Template anahtarlarına geç |
| `parse: FAILED` | `WHATSAPP_TEMPLATES_JSON` bozuk JSON | JSON’ı düzelt, tekrar çalıştır |
| Anahtar `PRESENT` | Gerekli şablon yapılandırılmış | Tekrar gönder testi hazır |
| Anahtar `MISSING` | Gerekli şablon eksik | JSON’a ekle, tekrar çalıştır |
| `RESULT: PASS` | Yapılandırma tamamlıyor | Manuel WhatsApp akış testi yapılabilir |
| `RESULT: FAIL` | Yapılandırma eksik/geçersiz | Manuel test **yapılmaz**, eksiklik giderilir |

Çıktı sadece değişken adı ve `SET`/`MISSING` durumu içerir. Gizli değerler asla yazdırılmaz.

## 6. Bildirim Şablonları, Olaylar, Alıcılar ve Parametre Sırası

Aşağıdaki eşleme yalnızca mevcut koddan (`src/persistence/prisma-notification.ts`) doğrulanmıştır. Template adı ve dil kodu `WHATSAPP_TEMPLATES_JSON`’ından gelir; parametre sırası kodda sabittir.

| Template key | Olay | Alıcı | Parametre sırası (koddan) |
|---|---|---|---|
| `appointment-created-staff` | APPOINTMENT_CREATED | Personel | 1. müşteri adı, 2. hizmet adı, 3. tarih/saat |
| `appointment-created-customer` | APPOINTMENT_CREATED | Müşteri | 1. hizmet adı, 2. tarih/saat, 3. personel adı |
| `appointment-confirmed-customer` | APPOINTMENT_CONFIRMED | Müşteri | 1. hizmet adı, 2. tarih/saat, 3. personel adı |
| `appointment-rejected-customer` | APPOINTMENT_REJECTED | Müşteri | 1. hizmet adı, 2. tarih/saat |

**Not:** Template parametre sayısı ve sırası `WHATSAPP_TEMPLATES_JSON`’ından güvenilir biçimde belirlenemez; JSON sadece `{ name, languageCode }` içerir. Parametre sırası yukarıdaki tablodaki gibi kodda sabittir ve bu runbook’da koddan doğrulanmıştır.

## 7. Pilot Tenant İçin WhatsAppIntegration Kaydı Önkoşulları

Webhook durumunu doğru tenant’a bağlamak için pilot tenant’ın bir `WhatsAppIntegration` kaydına ihtiyacı vardır. Mevcut kodda bu kayıt şu alanlara sahiptir: `id`, `tenantId`, `provider`, `phoneNumberId`, `status` (ACTIVE), `createdAt`, `updatedAt`. RLS zorunludur ve `phoneNumberId` webhook tenant çözümlemesi için anahtardır.

**Blokaj #7:** Mevcut kod deposunda pilot tenant için `WhatsAppIntegration` kaydı oluşturmak üzere seed dosyası veya SQL betiği yoktur. Yeni SQL uydurulmamalıdır. Gerekli bilgiler:

- Pilot tenant `id`
- Meta phone number ID (`phoneNumberId`)
- Provider değeri (`META_WHATSAPP`)
- `status` değeri (`ACTIVE`)

Bu bilgilerin onayını bekliyorum; onaylı olduğunda kayıt eklenebilir.

## 8. Test Senaryoları

### Senaryo 1 — Randevu Oluşturma → Bildirim
1. Test tenant’da aktif hizmet, çalışma saati ve personel yapılandırılır.
2. Test cihazından (müşteri) uygun bir slot seçilip randevu oluşturulur.
3. Randevu `PENDING` olarak kaydedilir.
4. Beklenen WhatsApp bildirimleri:
   - Personel’e `appointment-created-staff` (CREATED)
   - Müşteri’e `appointment-created-customer` (CREATED)
5. `NotificationDelivery` her alıcı için `PENDING` → gerçek gönderim sonrası `SENT` veya `FAILED`/`UNKNOWN` olmalıdır.

### Senaryo 2 — Personel Kararı → Bildirim
1. Personel randevuyu `CONFIRMED` veya `REJECTED` yapar.
2. Beklenen WhatsApp bildirimi:
   - Müşteri’e `appointment-confirmed-customer` veya `appointment-rejected-customer`
3. `NotificationDelivery` `PENDING` → `SENT`/`DELIVERED`/`FAILED`/`UNKNOWN` olmalıdır.

### Senaryo 3 — Müşteri Bildirimi ve Webhook
1. Webhook’tan `sent`/`delivered`/`failed` durumu gelirse, tenant-scoped `NotificationDelivery` güncellenmelidir.
2. `read` olayı veritabanını değiştirmemelidir.
3. Farklı bir tenant’ın `providerMessageId`sine yönelik webhook eventi fail-closed (hiçbir güncelleme olmamalı) olmalıdır.

## 9. Beklenen `NotificationDelivery` Durumları ve Webhook Doğrulama

| Girdi | Beklenen `NotificationDelivery` durumu | Açıklama |
|---|---|---|
| Başarılı gönderim | `SENT` | Provider mesajı kabul etti |
| Webhook `sent` | `SENT` (PENDING/UNKNOWN’den) | Webhook kurtarımı |
| Webhook `delivered` | `DELIVERED` (PENDING/SENT/UNKNOWN’den) | Webhook kurtarımı |
| Webhook `failed` | `FAILED` (PENDING/SENT/UNKNOWN’den) | Webhook kurtarımı |
| Provider hata/ağ | `UNKNOWN` | Belirsiz sonuç, tekrar gönderilmez |
| Webhook `read` | Değişiklik yok | READ veritabanını mutasyona uğratmaz |
| Bilinmeyen tenant (webhook) | Hiçbir güncelleme | Fail-closed, cross-tenant yok |
| İkinci aynı event (idempotency) | Yeniden gönderilmez | `already_sent` / `already_unknown` |

**Tenant-scoped webhook doğrulama adımları:**
1. Webhook imzası (`x-hub-signature-256`) doğrulanır (`WHATSAPP_APP_SECRET`).
2. `phone_number_id` üzerinden `resolve_whatsapp_tenant_id` ile tenant çözülür.
3. Çözülen tenant içinde `providerMessageId` eşleşen `NotificationDelivery` aranır.
4. Yalnızca desteklenen geçişler (`sent`→SENT, `delivered`→DELIVERED, `failed`→FAILED) uygulanır; `read` atlanır.
5. Bilinmeyen `phone_number_id` veya `providerMessageId` → fail-closed.

## 10. Riskler: UNKNOWN, Duplicate, Başarısız Teslimat ve Reconciliation

| Risk | Davranış | Not |
|---|---|---|
| UNKNOWN (provider belirsiz hata) | `UNKNOWN` olarak kaydedilir, **otomatik retry yok** | Manuel müdahale veya sonraki event ile kurtarılabilir |
| Duplicate send (aynı event tekrarı) | İdempotency anahtarı (`tenantId + appointmentId + eventType + channel + recipientProfileId`) ile engellenir | `already_sent` / `already_unknown` → provider çağrılmaz |
| Başarısız teslimat | `FAILED` (provider net hata) veya `UNKNOWN` (ağ/belirsiz) | Randevu lifecycle’ı geri alınmaz |
| Reconciliation | Webhook eventi `UNKNOWN`’ı `SENT`/`DELIVERED`/`FAILED`’e döndürebilir | Monotonic geçişler; eski olaylar durumu geriye almaz |
| Otomatik retry | **Yok** | Retry sadece manuel ve onaylı olabilir |

## 12. Başarı Ölçütleri, Temiz Durdurma ve Geri Alma/Temizlik

### Başarı ölçütleri

- `npm run whatsapp:preflight` `RESULT: PASS` verir.
- Dört şablon için de doğru olay/alıcı/parametre eşleşmesi doğrulanır.
- `NotificationDelivery` her alıcı için beklenen duruma ulaşır.
- Webhook `sent`/`delivered`/`failed` tenant-scoped güncellemesi yapar; `read` yapmaz.
- Farklı tenant webhook eventi fail-closed yapar.
- İdempotency: aynı event tekrarı provider’ı yeniden çağrmaz.
- Randevu lifecycle bildirim hatası nedeniyle geri alınmaz.

### Temiz durdurma koşulları

Aşağıdaki durumlarda test durdurulur ve onay beklenir:
- `whatsapp:preflight` `RESULT: FAIL` verir.
- Webhook tenant çözümlemesi bilinmeyen tenant için fail-closed değildir.
- `READ` olayı veritabanını mutasyona uğratır.
- Cross-tenant veri sızması tespit edilir.

### Geri alma / temizlik prosedürü

- Test tenant’ındaki test randevuları ve bildirim kayıtları test sonrası silinir veya devre dışı bırakılır.
- Test ortamında kullanılan `WhatsAppIntegration` kaydı test sonrası devre dışı bırakılır (`status` ≠ `ACTIVE`).
- Herhangi bir secret değer bu dokümana, test kanıtlarına veya terminal çıktısına yazılmamalıdır.
