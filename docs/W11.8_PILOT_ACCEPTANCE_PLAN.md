Tenant → Owner → Staff → Service → Working Hours → Public Vitrin → Customer Booking → Admin Calendar → Staff Decision → Staff Notification → Customer WhatsApp → Customer History

W11.8 is an acceptance phase, not a feature-expansion phase.

If an external prerequisite is unavailable, mark the scenario BLOCKED, not PASS.

## Required journey

### Tenant and owner

Verify real Supabase authentication, trusted app_metadata.tenant_id, TenantContext, membership/role authorization, and fail-closed behavior.

### Staff

Provision one pilot staff member. Verify Tenant A membership, ACTIVE state, inactive denial, and cross-tenant appointment denial.

### Catalog and availability

Configure an active service, duration/buffer, working hours, and active staff. Public booking must remain server-authoritative.

### Customer booking

On a real browser/device:

1. Open Tenant A public vitrin.
2. Select service.
3. Select staff where applicable.
4. Select date/time.
5. Enter customer details.
6. Submit.
7. Verify server result.
8. Verify appointment is PENDING.
9. Verify conflict/invalid-resource paths reject safely.

### Staff decision

Verify only authorized appointments are actionable, PENDING → CONFIRMED/REJECTED works, invalid transitions are rejected, and staff identity/profile binding is enforced.

### Notification

Using real Meta WhatsApp:

- CREATED reaches intended staff/customer recipients
- CONFIRMED reaches customer
- REJECTED reaches customer
- providerMessageId is persisted
- SENT/FAILED matches the existing domain
- duplicate delivery claim is idempotent
- provider failure does not mutate appointment lifecycle

### Customer history

Verify appointment history, lifecycle status, tenant-scoped notes, and direct-ID isolation.

### Webhook

After W11.6 validation:

- Meta phone_number_id resolves the correct tenant
- status updates remain tenant-scoped
- providerMessageId is resolved within the tenant boundary
- unknown phone numbers remain unresolved
- READ is parsed without inventing a new domain state

## Two-tenant acceptance

Use Tenant A and Tenant B with separate owners/staff, services, working hours, customers, appointments, notes, notification deliveries, and WhatsApp integrations where applicable.

Verify:

1. Tenant A reads only A.
2. Tenant A mutations cannot affect B.
3. Tenant A cannot retrieve B by direct identifier.
4. Missing tenant context returns no tenant-owned data.
5. Inactive membership/staff cannot operate.
6. Tenant A public booking cannot resolve Tenant B resources.

W11.7 regression evidence covers the database/security boundary but does not replace real pilot acceptance.

## Evidence policy

Record only:

- scenario ID
- timestamp
- non-secret environment identifier
- tenant label A/B
- actor role
- operation
- expected/observed result
- persisted domain status
- permitted provider reference
- PASS / FAIL / BLOCKED
- deviation

Never record access tokens, service-role keys, Meta tokens, app/webhook secrets, or unnecessary customer PII.

## Exit criteria

W11.8 is PASS only when:

- mandatory real-pilot scenarios pass
- no critical security scenario fails
- W11.4 real Supabase validation passes
- W11.5 real Meta validation passes
- W11.6 webhook routing is validated if included
- W11.7 regression passes
- mobile/PWA core workflow works on a real pilot device
- appointment lifecycle remains correct
- notification failure does not mutate lifecycle
- deviations and remaining risks are documented

BLOCKED cannot silently become PASS.

## Out of scope

W11.8 does not authorize production deployment, native mobile implementation, appointment state-machine changes, tenant-model changes, RLS weakening, new notification channels, unapproved migrations, or silent MVP expansion.

Production deployment remains a separate W11.9 human-approval checkpoint.
