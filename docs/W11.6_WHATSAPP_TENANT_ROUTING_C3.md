# W11.6 — WhatsApp Webhook Tenant Routing C3 Decision

## Status

**C3 decision required before implementation.**

W11.5 is merged. W11.6 must connect inbound Meta WhatsApp webhook status events to the correct tenant-scoped NotificationDelivery without weakening tenant isolation or inventing a new notification lifecycle state.

## Problem

Meta webhook status payloads provide provider-side identifiers such as `phone_number_id` and `providerMessageId`. The current webhook route can verify the request and parse status events, but it intentionally does not persist them because provider-message-id to tenant routing is not established.

Routing must therefore establish:

`Meta phone_number_id → tenant-scoped WhatsApp integration → tenantId → NotificationDelivery`

Then the provider message identifier can be resolved only inside that trusted tenant context.

## Proposed Architecture

### 1. Tenant-scoped integration record

Introduce a tenant-owned `WhatsAppIntegration` model:

- `id`
- `tenantId`
- `provider`
- `phoneNumberId`
- `status`
- created/updated timestamps as consistent with existing project conventions

Required invariants:

- one Meta WhatsApp phone number belongs to one tenant integration;
- `phoneNumberId` is the external routing key;
- the record is tenant-owned and protected by PostgreSQL RLS;
- no client-controlled tenant identifier participates in webhook routing;
- webhook routing must not infer tenant from request body fields other than the provider routing identifier.

### 2. Routing algorithm

1. Verify Meta webhook signature using the existing raw-body HMAC boundary.
2. Parse the webhook payload.
3. Extract the provider `phone_number_id`.
4. Resolve the active `WhatsAppIntegration` by provider + `phoneNumberId`.
5. Obtain the trusted `tenantId` from that integration.
6. Enter the existing tenant DB context.
7. Resolve `NotificationDelivery.providerMessageId` within that tenant.
8. Apply only status transitions already supported by the domain.
9. Unknown integration, unknown provider message, malformed event, or persistence failure must fail closed without cross-tenant lookup.

### 3. Notification status mapping

The current domain enum is:

`PENDING | SENT | DELIVERED | FAILED`

The webhook parser recognizes:

- sent
- delivered
- failed
- read

C3 decision: **do not add READ to the domain enum in W11.6.**

Proposed mappings:

- Meta `sent` → `SENT`
- Meta `delivered` → `DELIVERED`
- Meta `failed` → `FAILED`
- Meta `read` → no domain mutation in W11.6

A READ-specific product requirement would require a separate C3 decision.

### 4. providerMessageId

The current delivery record stores nullable `providerMessageId` and the delivery idempotency key remains:

`tenantId + appointmentId + eventType + channel + recipientProfileId`

C3 decision: **do not make providerMessageId globally unique.**

Tenant-aware lookup is the security boundary. An index may be added if required by the implementation, but uniqueness semantics must not change without separate approval.

### 5. Migration boundary

W11.6 is expected to require a Prisma migration for `WhatsAppIntegration`.

No migration may be generated/applied until this C3 is explicitly approved.

The migration must include:

- tenant relation;
- provider/phoneNumberId routing fields;
- appropriate uniqueness/indexing;
- RLS enablement and forced RLS;
- tenant ownership policies consistent with existing tenant-owned tables.

No existing tenant/RLS policy may be weakened.

### 6. Webhook failure behavior

Webhook handling must distinguish:

- invalid signature → reject;
- invalid verification token → reject;
- malformed/unsupported payload → reject or safely acknowledge according to the existing route contract;
- unknown `phoneNumberId` → no tenant resolution;
- unknown `providerMessageId` within resolved tenant → no delivery mutation;
- persistence failure → no partial cross-tenant mutation.

The implementation must preserve the existing provider-neutral NotificationService boundary. Webhook processing is provider-specific infrastructure and must not modify appointment lifecycle state.

## Security Acceptance Criteria

- Tenant A webhook cannot update Tenant B delivery.
- A provider message identifier is never searched without first establishing tenant context from the integration.
- No client/session identity is used for webhook tenant routing.
- Missing integration fails closed.
- Missing delivery fails closed.
- RLS remains enabled and forced.
- Existing tenant context is transaction-local.
- No appointment status is changed by webhook processing.
- No READ lifecycle state is invented.

## Implementation Gate

After C3 approval:

1. Add Prisma model + migration.
2. Add RLS policies and migration review.
3. Add tenant-scoped WhatsApp integration repository/application boundary.
4. Update webhook route to resolve integration and delivery inside trusted tenant context.
5. Add tests for routing, unknown integration, unknown provider message, cross-tenant isolation, status mapping, signature failure, and persistence failure.
6. Run migration, lint, typecheck, tests, build.
7. Open PR.
8. CI must pass.
9. Human review and merge approval required.

## Explicitly Out of Scope

- Meta webhook subscription/deployment changes.
- Production deployment.
- Appointment state-machine changes.
- READ notification state.
- Client-side tenant selection.
- Global providerMessageId uniqueness.
- NotificationService redesign.
- Native mobile application work.
- Any unrelated schema cleanup.

## Open C3 Question

**Approve the proposed `WhatsAppIntegration` tenant-routing model and the webhook routing/status-mapping rules above, with the explicit constraint that READ remains non-mutating and providerMessageId remains non-globally-unique.**
