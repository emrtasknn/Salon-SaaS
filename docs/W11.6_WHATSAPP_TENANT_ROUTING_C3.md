# W11.6 — WhatsApp Webhook Tenant Routing C3 Decision

## Status

**C3 APPROVED — 2026-11-01. Implementation and security verification remain open.**

The project owner approved the proposed tenant-scoped WhatsApp webhook routing model and status rules on 2026-11-01.

Approval constraints:
- Meta `read` status does not mutate NotificationDelivery in W11.6.
- `providerMessageId` is not globally unique.
- Tenant resolution must be derived from the trusted provider integration, never from a client-supplied tenant ID.
- No production deployment is authorized by this decision.

## Existing implementation discovered during approval review

Read-only inspection of current `main` found that some W11.6 building blocks already exist:

- `prisma/schema.prisma` contains `WhatsAppIntegration` with `tenantId`, `provider`, `phoneNumberId`, `status`, a tenant relation, unique `[provider, phoneNumberId]`, and tenant index.
- `src/app/api/webhooks/whatsapp/route.ts` verifies the raw-body Meta signature, parses status events, groups by `phoneNumberId`, calls `resolveWhatsAppTenantId`, then applies statuses in a tenant context.
- `src/infrastructure/meta-whatsapp-webhook.ts` parses sent/delivered/failed/read and verifies HMAC signatures.
- `src/persistence/prisma-whatsapp-webhook.ts` calls `private.resolve_whatsapp_tenant_id(phoneNumberId)` and applies tenant-filtered status updates; `read` is ignored.

This is source inspection only. It does **not** prove that the migration, SQL resolver function, RLS/forced-RLS policies, database grants, or runtime behavior are correct. Do not assume a new Prisma model or migration is needed: inspect existing migrations first and reconcile schema drift before creating any migration.

## Approved architecture

Routing:

`Meta phone_number_id → active WhatsAppIntegration → trusted tenantId → tenant-scoped NotificationDelivery.providerMessageId`

1. Verify Meta webhook signature using the existing raw-body HMAC boundary.
2. Parse webhook payload and extract provider `phone_number_id`.
3. Resolve the active integration by provider + `phoneNumberId`.
4. Obtain trusted `tenantId` from that integration.
5. Enter existing tenant DB context.
6. Resolve `NotificationDelivery.providerMessageId` only inside that tenant.
7. Apply only supported status transitions.
8. Unknown integration/message, malformed event, or persistence failure must fail closed without cross-tenant lookup or mutation.

## Approved status mapping

- Meta `sent` → `SENT`
- Meta `delivered` → `DELIVERED`
- Meta `failed` → `FAILED`
- Meta `read` → no domain mutation in W11.6

Do not add a READ enum or change appointment lifecycle state.

## Approved provider message ID policy

The delivery idempotency key remains:

`tenantId + appointmentId + eventType + channel + recipientProfileId`

Do not make `providerMessageId` globally unique. Tenant-aware lookup is the security boundary. Add a non-unique index only if justified by measured query needs and migration review.

## Required implementation/security audit before W11.6 can close

1. Inspect all existing migrations for `WhatsAppIntegration`, `private.resolve_whatsapp_tenant_id`, grants, RLS and FORCE RLS.
2. Verify resolver function security posture: schema qualification, search_path, execute grants, function owner/privileges, input validation, active integration filtering, and no tenant leakage.
3. Verify the resolver is the only pre-tenant lookup and returns only the tenant ID for a unique active integration.
4. Verify `applyWhatsAppWebhookStatuses` uses transaction-local tenant context and every mutation includes tenantId.
5. Verify RLS is enabled and forced where required, policies match established tenant-owned table patterns, and service-role/bypass privileges are understood.
6. Verify state transition monotonicity: delayed `sent` events must not downgrade `DELIVERED` or overwrite `FAILED`; define and test allowed transitions explicitly.
7. Add/verify tests for unknown/inactive integration, unknown provider message, duplicate webhook events, cross-tenant isolation, status ordering, READ no-op, invalid signature, malformed payload, and persistence failure.
8. Run migration drift checks, lint, typecheck, unit/integration tests, and build against an isolated test database.
9. Open a PR; CI must pass; human review and explicit merge approval are required.

## Security acceptance criteria

- Tenant A webhook cannot update Tenant B delivery.
- Provider message ID is never searched before trusted tenant resolution.
- No client/session identity participates in webhook tenant routing.
- Missing/inactive integration fails closed.
- Missing delivery causes no mutation.
- RLS remains enabled and forced where required.
- Tenant context is transaction-local.
- No appointment status is changed by webhook processing.
- READ causes no domain mutation.
- Delayed or duplicated status events cannot regress a terminal delivery state.

## Explicitly out of scope

- Meta webhook subscription/deployment changes.
- Production deployment.
- Appointment state-machine changes.
- READ notification state.
- Client-side tenant selection.
- Global providerMessageId uniqueness.
- NotificationService redesign.
- Native mobile application work.
- Unrelated schema cleanup.
