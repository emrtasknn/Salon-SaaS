# W11.4 — Real Supabase Pilot Validation Plan

Status: EXECUTED VALIDATION PLAN — TWO-TENANT ISOLATION MANUALLY PASSED; remaining criteria retain their own evidence status

## Objective

Validate the existing authentication, trusted tenant binding, membership authorization, RLS isolation, staff provisioning, inactive-staff behavior, and failure/rollback boundaries against a production-like Supabase project.

This phase is validation-first. It does not introduce a new product feature or change the established security architecture.

- W11.1 audit: PASS WITH OPEN ITEMS.

- Existing authorization remains TenantMembership + role.

## Non-goals

Do not change:
- tenant model
- trusted identity source
- authorization policy composition
- RLS semantics
- appointment state machine
- booking conflict algorithm
- NotificationService/provider boundary
- production deployment authority
- MVP scope

Do not add a new migration unless a previously unknown blocking gap is discovered and separately approved.

## Pilot environment

Use a dedicated production-like Supabase project/environment that is isolated from production data.

Required capabilities:
- Supabase Auth enabled
- application database migrations applied
- test owner account
- test staff account/invitation path
- at least two isolated tenant records for cross-tenant checks
- controlled test data
- server runtime configured with required server-side credentials

Secrets must remain in environment/secret storage and must never be committed, logged, or exposed to the client bundle.

## Validation matrix

### A. Owner authentication

1. Authenticate the pilot owner through the supported application flow.
2. Confirm the authenticated server request resolves the Supabase Auth subject.
3. Confirm missing/invalid authentication fails closed.
4. Confirm the application does not trust client-provided subjectId, tenantId, or role.

Expected result: authenticated owner reaches only the tenant authorized by the trusted identity path.

### B. Trusted tenant binding

1. Provision/bind the owner using the existing tenant binding flow.
2. Verify `app_metadata.tenant_id` is the tenant authority.
3. Verify TenantContext resolves from trusted server-side identity.
4. Verify a missing tenant claim is rejected.
5. Verify an invalid tenant claim cannot produce an authorized context.

Expected result: tenant authority comes only from the established trusted identity boundary.

### C. Membership and role authorization

1. Verify owner/TENANT_ADMIN access succeeds for its own tenant.
2. Verify a user without the required membership is rejected.
3. Verify an authenticated user with an incorrect role is rejected.
4. Verify membership persistence failures fail closed.

Expected result: authorization is determined server-side by membership and role.

### D. Staff invitation/provisioning

1. Execute the supported staff provisioning/invitation path.
2. Verify the Auth identity is created/invited.
3. Verify Profile and TenantMembership are created for the correct tenant.
4. Verify Staff is created with the expected active/inactive lifecycle semantics.
5. Exercise the documented compensation/rollback behavior for a controlled failure.
6. Verify a failed provisioning attempt does not leave an incorrectly authorized staff record.

Expected result: staff provisioning preserves tenant binding and fail-closed behavior.

### E. RLS isolation

Use Tenant A and Tenant B.

1. Authenticate an actor authorized for Tenant A.
2. Read Tenant A records.
3. Attempt direct identifier access to Tenant B records through supported application/persistence paths.
4. Attempt mutation of Tenant B records.
5. Repeat for customer/profile, staff, service, appointment, working hours, notes, memberships, and notification delivery records where applicable.
6. Verify absent tenant DB context fails closed.
7. Verify transaction-local tenant context does not leak between operations.

Expected result: Tenant A cannot read, mutate, or infer Tenant B data.

### F. Inactive staff behavior

1. Mark a pilot staff member inactive through the supported operation.
2. Verify staff cannot perform authorized staff appointment actions.
3. Verify inactive staff does not become selectable/usable where existing domain rules prohibit it.
4. Verify tenant admin behavior remains correctly scoped.

Expected result: inactive staff loses the applicable staff authority without affecting unrelated tenant data.

### G. Failure and rollback boundaries

Exercise controlled failures at:
- auth binding
- membership lookup
- staff provisioning
- persistence transaction

Verify:
- fail-closed response
- no accidental cross-tenant authorization
- no partial authorization state
- documented compensation/rollback behavior
- existing error/result contracts remain stable

Do not force destructive production-like failures against shared or production data.

## Evidence requirements

Record for each scenario:
- scenario identifier
- environment identifier (non-secret)
- actor/tenant role
- action
- expected result
- observed result
- pass/fail
- relevant application/CI evidence
- deviation or follow-up

Never record:
- access tokens
- service-role keys
- passwords
- webhook secrets
- personal production data

## Execution update — 2026-10-31

The project owner confirmed that the real environment already contains two distinct tenants, with separate salon details and staff. The owner has repeatedly exercised the application manually and confirmed reciprocal isolation: Tenant A accesses only its own data and cannot access Tenant B data; Tenant B accesses only its own data and cannot access Tenant A data.

This closes the plan's prerequisite that at least two real tenant records be available and records the manual two-tenant isolation scenario as **PASS**.

Evidence boundary:
- Classification: owner-reported manual validation against the existing real environment.
- No tenant records were created or modified for this documentation update.
- This note does not claim that every resource type, direct-ID mutation path, or the separately specified cross-tenant public-booking edge case was individually exercised.
- Automated RLS evidence remains separately recorded in the acceptance packet; manual validation does not replace automated regression coverage.
