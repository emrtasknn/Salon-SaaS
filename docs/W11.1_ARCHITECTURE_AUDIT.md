## 1. Authentication / trusted identity

**Result: PASS architecturally; real Supabase validation remains OPEN.**

Evidence:
- Supabase adapter reads the authenticated Supabase subject ID.
- Tenant authority is read from Supabase `app_metadata.tenant_id`.
- Missing/invalid authentication fails closed.
- `user_metadata` is not used as tenant authority.
- Authenticated tenant requests construct a trusted TenantContext from the server-side auth snapshot.

Remaining validation:
- Real production-like Supabase project.
- Real owner authentication.
- Real staff provisioning/invitation.
- Real app_metadata tenant binding.

## 2. Membership / role authorization

**Result: PASS.**

Evidence:
- Authorization composition performs membership lookup using the trusted tenant context and authenticated subject.
- Membership lookup errors fail closed.
- Missing membership fails authorization.
- Role authorization is evaluated server-side.

No change required before W11.2.

## 3. Tenant database context / RLS

**Result: PASS for reviewed tenant-owned tables.**

Evidence:
- Tenant database context starts a transaction.
- `app.tenant_id` is set transaction-locally.
- Operation commits only after successful execution; errors roll back.
- Reviewed tenant-owned tables have RLS enabled/forced with tenant-aware policies, including:
  - Profile
  - Staff
  - Service
  - Appointment
  - TenantMembership
  - WorkingHours
  - CustomerNote
  - NotificationDelivery
- Existing RLS integration tests cover:
  - matching tenant access
  - mismatched tenant blocking
  - missing tenant context blocking
  - transaction-local context cleanup

Important correction:
- An earlier audit hypothesis that WorkingHours, CustomerNote or NotificationDelivery lacked RLS was disproven by their dedicated migrations. No RLS weakening or migration is required from this finding.

W11.2 must not alter these domain semantics.

## 5. Public booking UX

**Result: OPEN — W11.2 required.**

Current implementation still exposes internal identifiers as product UX:
- Service ID input
- Staff ID input
- raw datetime-local input

The approved UX contract requires:

`service → staff → date/time → customer details → submit → result`

Required result handling includes:
- success
- invalid input
- slot unavailable
- invalid resource
- persistence failure

Current server contract already distinguishes these outcomes, but the UI compresses them into a minimal status message.

Known implementation improvement:
- `createPublicBooking` currently returns only status.
- `submitBooking` performs a post-create appointment lookup by tenant/service/staff/startAt before publishing APPOINTMENT_CREATED.
- W11.2 should evaluate returning `appointmentId` directly from the application contract to remove this lookup and make notification publication deterministic.

This is an application-contract improvement, not a booking-semantic change.

## 6. Notification / WhatsApp runtime

**Result: PASS boundary; real provider validation OPEN.**

Evidence:
- Meta WhatsApp provider is behind the NotificationProvider interface.
- Runtime is marked `server-only`.
- Meta access token, phone number ID, API version and templates are read from server environment variables.
- Missing/invalid runtime configuration produces NOT_CONFIGURED.
- Provider failure does not directly mutate appointment lifecycle semantics.

Real validation still required:
- real Meta API
- approved templates
- successful provider response
- provider message ID persistence
- duplicate/idempotency behavior
- failure behavior
- staff/customer recipient mapping

## 7. WhatsApp webhook

**Result: BLOCKED for implementation until C3 architecture decision.**

Current behavior:
- GET verification checks the configured webhook verification token.
- POST verifies the raw request body with HMAC-SHA256 and timing-safe comparison.
- Meta statuses are parsed for sent/delivered/failed/read.
- Status persistence is intentionally not performed because provider-message-id → tenant routing is not yet authoritative.

Required C3 decision:
`Meta phone_number_id → tenant-scoped WhatsAppIntegration → tenantId → NotificationDelivery → providerMessageId`

The candidate `WhatsAppIntegration` schema is not approved yet.

The current domain enum does not contain READ. W11.6 must explicitly decide the supported delivery-status mapping; no READ state is to be invented silently.

## 8. CRM

**Result: OPEN — W11.3 required.**

Existing customer history and notes foundations are present.

Missing pilot workflow:
`Customer List → Search → Customer Detail → Appointment History → Notes`

All customer reads/writes must remain tenant-scoped and server-authorized.

## 9. UI/UX contract

**Result: PASS as governance; implementation gap confirmed in public booking.**

The W10 booking contract requires server-authoritative result handling and prohibits promising availability solely from client-side calculation.

The current public booking screen does not yet implement the intended catalog-driven flow. W11.2 is the correct remediation point.

## 10. Environment / secret boundary

**Result: PASS for inspected notification/auth runtime boundary.**

Evidence:
- WhatsApp runtime is server-only.
- Meta credentials are read from server environment variables.
- No client-side Meta credential usage was found in the inspected runtime files.
- Webhook secrets are read server-side.

Remaining W11.4/W11.5 validation:
- deployment environment configuration
- client bundle inspection in pilot-like build
- real Supabase and Meta secret configuration

## 11. Two-tenant security regression

**Result: OPEN — W11.7 required.**

Current RLS integration coverage is useful but intentionally narrow.

W11.7 must add explicit Tenant A / Tenant B coverage for:
- records
- appointments
- customers
- notes
- notifications
- staff actions
- public booking resource boundaries
- direct identifier manipulation
- missing tenant context
- inactive membership/staff

Acceptance:
Tenant A must not read, mutate, or infer Tenant B data through supported application surfaces.
