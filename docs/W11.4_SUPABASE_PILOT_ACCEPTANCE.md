### G. Two-tenant isolation — MANUAL REAL-ENVIRONMENT VALIDATION PASS

The project owner has confirmed that the real application/database environment contains **two distinct tenants**, each with its own salon identity/details and its own staff records.

The owner manually exercised the tenant boundary repeatedly and confirmed:

- Tenant A can access its own tenant data.
- Tenant A cannot access Tenant B's data.
- Tenant B can access its own tenant data.
- Tenant B cannot access Tenant A's data.
- Each tenant sees/uses its own staff rather than the other tenant's staff.

Result: **PASS — the two-tenant isolation scenario has been manually exercised against the existing real environment.** This closes the previously documented gap that incorrectly stated a second tenant was unavailable.

Evidence classification and limits:

- This is owner-reported, repeated manual application validation, recorded on 2026-10-31.
- It is distinct from the automated real-Supabase PostgreSQL RLS suite (5/5 scenarios) and from the PostgreSQL 17 CI integration suite.
- No claim is made here that every possible table, direct-ID path, mutation path, or the specific authenticated cross-tenant public-booking edge case was individually exercised unless separately recorded.
- No new tenant was created as part of this documentation update, and no database data was changed by this documentation update.

The existing server-side trusted tenant context, membership/role authorization, tenant-scoped persistence, and RLS remain the required enforcement layers.
