# W11.5 — Real Meta WhatsApp Pilot Validation Plan

Status: ARCHITECT PLAN — HUMAN APPROVAL REQUIRED BEFORE EXECUTION

## Objective

Validate the existing provider-neutral NotificationService and Meta WhatsApp Cloud API provider against a real Meta WhatsApp Business environment without changing appointment lifecycle semantics, tenant authority, or notification architecture.

## Current baseline

- W11.4 remains external-validation-pending.
- Existing provider boundary: Appointment Event → NotificationService → NotificationProvider → MetaWhatsAppProvider.
- Runtime configuration is server-only.
- NotificationDelivery persists provider message IDs and SENT/FAILED state.
- Notification idempotency is tenant + appointment + event + channel + recipient profile.
- WhatsApp webhook status persistence remains intentionally blocked until W11.6 tenant routing is architecturally approved.
- No schema migration is planned for W11.5.

## Validation scope

### A. Runtime configuration

Verify in an isolated pilot environment:
- WHATSAPP_ACCESS_TOKEN configured server-side
- WHATSAPP_PHONE_NUMBER_ID configured server-side
- WHATSAPP_API_VERSION configured server-side
- WHATSAPP_TEMPLATES_JSON configured server-side
- WHATSAPP_WEBHOOK_VERIFY_TOKEN and WHATSAPP_APP_SECRET are not exposed to client code

Missing/invalid configuration must resolve to the existing NOT_CONFIGURED behavior.

Never record secrets in evidence.

### B. Template validation

For each configured MVP notification template:
1. Verify the template exists and is approved in the Meta environment.
2. Verify template key → Meta template name mapping.
3. Verify language code.
4. Verify body parameter count/order matches the application payload.
5. Verify the provider sends template messages rather than arbitrary text.

A template mismatch is a validation failure; do not silently alter runtime behavior to accommodate it.

### C. Real outbound delivery

Exercise the existing events:
- APPOINTMENT_CREATED → staff + customer
- APPOINTMENT_CONFIRMED → customer
- APPOINTMENT_REJECTED → customer

For each:
1. Trigger the existing application lifecycle action.
2. Verify NotificationService recipient mapping.
3. Verify Meta accepts the message.
4. Verify providerMessageId is returned.
5. Verify NotificationDelivery transitions to SENT.
6. Verify recipient receives the WhatsApp message on the pilot device.

Appointment lifecycle success must not depend on provider delivery success.

### D. Failure behavior

Controlled pilot checks:
- missing template
- invalid/expired provider credential in a non-production test environment
- invalid recipient number where Meta safely rejects it
- provider HTTP failure

Expected:
- NotificationDelivery becomes FAILED through the existing service boundary.
- Appointment lifecycle is not rolled back solely because notification delivery failed.
- No secret or access token appears in application logs/evidence.
- Existing error/status contracts remain intact.

Restore valid configuration after each negative test.

### E. Idempotency / duplicate behavior

Trigger the same appointment event more than once.

Expected:
- existing NotificationDelivery uniqueness prevents duplicate delivery claims for the same tenant/appointment/event/channel/recipient.
- repeated publish does not create a second successful delivery for an already-sent recipient.
- provider is not called after an already-sent claim.

Do not weaken or bypass the current idempotency boundary.

### F. Staff/customer recipient mapping

Validate real recipient routing:
- CREATED reaches the intended staff and customer recipients.
- CONFIRMED reaches the intended customer.
- REJECTED reaches the intended customer.
- wrong-tenant recipient data cannot be selected through supported application paths.

## Webhook boundary

W11.5 does NOT complete inbound webhook tenant routing.

Current verified webhook behavior:
- GET verify-token challenge.
- POST raw-body HMAC verification.
- status parsing.

Status persistence is deferred to W11.6 because provider message ID alone is not yet tenant-routable without an approved tenant-scoped integration boundary.

Do not mark delivery/read webhook synchronization as complete in W11.5.

## Evidence

Record:
- scenario ID
- environment identifier (non-secret)
- notification event
- template key
- recipient role (staff/customer)
- provider acceptance/result
- application NotificationDelivery status
- providerMessageId only if policy permits; otherwise record a redacted reference
- observed device result
- pass/fail
- deviation

Never record:
- access tokens
- app secrets
- webhook secrets
- customer production PII

## Exit criteria

W11.5 passes only if:
- real Meta template configuration is validated
- real outbound messages are accepted and delivered
- providerMessageId persistence works
- SENT/FAILED behavior matches the existing domain
- duplicate/idempotency behavior passes
- staff/customer recipient mapping passes
- provider failures do not mutate appointment lifecycle state
- secret boundaries remain intact
- webhook tenant routing remains explicitly OPEN for W11.6

Real provider delivery is not considered validated from mocks or CI alone.

## Dependencies and sequencing

- W11.4 real Supabase validation remains pending and should be completed before final pilot acceptance.
- W11.6 requires a separate C3 architecture decision before schema or implementation changes.
- W11.7 two-tenant security regression remains required.
- W11.5 does not authorize production deployment.
